# Day07 模拟卷 · 科目二：案例分析（试题与参考答案）

> **本卷共 5 道大题，考生任选 3 道作答，其中第 1 题为必答题；第 2-5 题中任选 2 题。每题 25 分，建议限时 90 分钟。**

## 试题一（必答，25 分）

某高校图书馆拟建设借阅管理系统，经需求分析得到如下业务描述：
（1）每位读者拥有唯一校园卡，卡随读者档案的建立而发放、注销而失效；读者凭卡借书，每卡同时在借上限 5 册，借期 30 天，逾期按每天 0.5 元计罚金；
（2）每册馆藏图书贴有唯一条码，系统登记其馆藏状态（在馆/外借/预约保留）；
（3）管理员办理借出与归还；归还时系统自动检查是否逾期，逾期则生成缴款记录；
（4）读者可对全部外借的图书发起预约，到书后系统保留 2 天，逾期未取自动释放并通知下一位预约者。

**【问题1】**（9 分）从上述描述中识别核心实体类（至少 4 个），画出类图的主要关系（用文字描述每个类之间的关系类型与多重性），并说明其中"读者—校园卡"为什么是组合关系而"读者—借阅记录"是关联关系。
**【问题2】**（8 分）为"借阅记录"对象绘制状态图（列出状态、事件与动作），覆盖正常借还与逾期分支。
**【问题3】**（8 分）用顺序图描述"借书"用例的对象交互过程（读者→借阅界面→借阅控制器→读者档案→借阅记录→馆藏图书），并说明顺序图与通信图（协作图）的关系。

## 试题一 参考答案

**【问题1】（9 分）**
核心实体类：读者（Reader）、校园卡（Card）、借阅记录（BorrowRecord）、馆藏图书（BookItem）、预约记录（Reservation）、缴款记录（Fine）（每答出 4 个给 2 分，共 4 分）。
主要关系（3 分，类型与多重性正确即可）：
- 读者 1——1 校园卡：**组合**（实心菱形）；
- 读者 1——0..* 借阅记录：**关联**；
- 借阅记录 1——1 馆藏图书：**关联**（一册同时至多一条在借记录）；
- 读者 1——0..* 预约记录、馆藏图书 1——0..* 预约记录：**关联**；
- 借阅记录 1——0..1 缴款记录：**关联**。
辨析（2 分）：校园卡的生命周期与读者档案**完全绑定**（建档案即发卡、注销即失效），部分不能脱离整体独立存在，故为组合；借阅记录是业务事件发生后形成的独立业务对象，读者档案注销后历史借阅记录仍需保留（如审计），可脱离读者对象独立存在，故为普通关联。**判据是生命周期是否绑定，不是关系的亲疏**。

**【问题2】（8 分）**
借阅记录状态图（状态 6 个各 0.5 分共 3 分，事件/动作 5 分，画出等价形式均可）：

```
[已创建]──借出──▶[在借]──按期归还──▶[已归还]──▶[关闭]
                    │  ▲                 │
              超期事件│  │（不改变在借语义）  └─逾期判定─▶[待缴款]
                    ▼  │                              │
                 [逾期在借]──逾期归还──▶[已归还]        缴款
                    │                                    ▼
                    └──────────────────────────────▶[关闭]
```
- 状态：已创建、在借、逾期在借、已归还、待缴款、关闭；
- 事件：借出、归还（按期/逾期）、超期（系统定时触发）、缴款；
- 动作：归还时检查逾期并计算罚金（金额＝逾期天数×0.5 元）、生成缴款记录、更新馆藏状态为"在馆"。

**【问题3】（8 分）**
顺序图交互过程（5 分，对象与消息序列正确即可）：
1. 读者→借阅界面：刷卡并提交借书请求（含条码）；
2. 借阅界面→借阅控制器：borrow(cardNo, bookBarcode)；
3. 借阅控制器→读者档案：查询读者状态与在借数量（返回：正常、在借 3 册）；
4. 借阅控制器→馆藏图书：查询馆藏状态（返回：在馆）；
5. 借阅控制器→借阅记录：创建借阅记录（借出日期＋30 天应还日期）；
6. 借阅控制器→馆藏图书：更新状态为"外借"；
7. 返回借书成功消息→借阅界面→读者（打印凭条）。
顺序图与通信图的关系（3 分）：二者**语义等价**、可相互转换，都描述对象交互——顺序图按时间轴纵向排列消息，**强调消息的时间顺序**；通信图以对象为节点、消息加编号，**强调对象间的组织链接结构**。选用原则：分析时序与生命周期选顺序图，分析对象协作结构选通信图。

## 试题二（选答，25 分）

某在线商城系统在迭代改造中遇到四个设计问题：
① 结算时需支持支付宝、微信、银联等多种支付渠道，渠道后续还会增加，且运营可随时配置切换默认渠道；
② 订单状态变化（已支付/已发货/已签收）需同时通知库存、物流、短信等多个模块，通知对象还会增加；
③ 需要接入的第三方物流查询接口各不相同，而商城物流模块的统一接口早已固定；
④ 系统配置信息须全局唯一且懒加载。

**【问题1】**（8 分）为四个问题分别选择最合适的设计模式，并各用一句话说明选择理由。
**【问题2】**（9 分）以问题②为例，说明观察者模式的结构（角色与核心方法）及其如何使系统满足开闭原则。
**【问题3】**（8 分）若问题①的实现为：在结算代码中用 if-else 逐个判断渠道类型、每新增渠道就修改该段代码。分析该实现违反了哪些设计原则，给出重构思路。

## 试题二 参考答案

**【问题1】（8 分，每个 2 分）**
① **策略模式**（行为型）：将每种支付渠道封装为可互换的算法族，渠道增减与切换不影响结算模块；
② **观察者模式**（行为型）：订单作为目标对象，通知方作为观察者注册订阅，状态变化自动通知，新增通知方无需修改订单模块；
③ **适配器模式**（结构型）：将各第三方物流接口转换（适配）为商城统一的物流查询接口，不修改既有模块；
④ **单例模式**（创建型）：保证配置对象全局唯一实例并提供统一访问点，配合懒加载与线程安全实现。

**【问题2】（9 分）**
结构（5 分）：**抽象目标 Subject**（订单状态管理器：attach(observer)、detach(observer)、notify()）与**抽象观察者 Observer**（update(status)）；具体目标（OrderSubject）维护观察者集合与订单状态，状态变化时遍历集合调用 update；具体观察者（库存模块、物流模块、短信模块）各自实现 update 完成自己的响应逻辑。
与开闭原则的关系（4 分）：新增"积分模块"通知方时，只需编写新的具体观察者类并调用 attach 注册——**通过扩展（新增类）应对变化，不修改订单模块任何代码**，即"对扩展开放、对修改关闭"；同时订单与通知方仅通过 Observer 抽象耦合，实现了高层与细节均依赖抽象的依赖倒置，订单无需知道通知方的具体类型与数量。

**【问题3】（8 分）**
违反的原则（4 分）：**开闭原则**——每新增渠道都要修改结算源码，扩展以修改既有代码为代价；**单一职责原则**——结算逻辑与渠道选择分发混在一处，渠道变化成为结算代码的变化来源之一；若渠道判断散布多处，还违反**迪米特法则**（结算对象被迫了解每种渠道的细节）。
重构思路（4 分）：定义统一的支付接口 PaymentStrategy（含 pay(amount) 等方法），每种渠道实现该接口；结算模块仅依赖抽象接口，具体策略由配置（渠道编码→策略类映射）在运行时注入；新增渠道＝新增一个策略实现类＋一条配置，结算代码零修改——同时满足开闭与依赖倒置，且便于对结算逻辑做独立的单元测试（可用桩策略替换真实渠道）。

## 试题三（选答，25 分）

评审员对某订单处理系统的设计提出三段审查记录：
（1）类 OrderService 共 600 余行，同时负责订单校验、计价、库存扣减、发票生成与邮件发送，任何一处规则变化都修改该类并触发全量回归测试；
（2）为复用面积计算代码，让正方形类 Square 继承长方形类 Rectangle，并继承其 setWidth/setHeight 方法；某客户端按"先 setWidth(5) 再 setHeight(4) 计算面积"使用时，对正方形得到了错误结果；
（3）高层报表类 Report 中直接 new 具体类 OracleDao 完成数据访问，切换 MySQL 数据库时被迫修改 Report 源码。
另外，评审员对核心方法 calcPrice 的控制流图进行了度量：节点数 N＝8，边数 E＝9，其中判定节点 2 个。

**【问题1】**（9 分）逐条判断（1）（2）（3）分别违反了哪条面向对象设计原则，说明判断依据与危害。
**【问题2】**（8 分）用两种方法计算 calcPrice 的圈复杂度，说明该指标的含义与行业经验阈值。
**【问题3】**（8 分）给出（3）的重构方案，说明重构后设计如何满足依赖倒置与开闭原则、可测试性为何提升。

## 试题三 参考答案

**【问题1】（9 分）**
（1）违反**单一职责原则**（3 分）：校验、计价、库存、发票、邮件五类职责＝五个变化来源集中在一个类，任何变化都修改该类，牵一发动全身、回归范围失控。
（2）违反**里氏替换原则**（3 分）：正方形作为子类替换长方形后，setWidth(5) 与 setHeight(4) 因"四边相等"约束相互影响，无法保持父类"宽高独立设置"的行为语义，客户端按父类契约使用即出错——子类不能无差别替换父类。
（3）违反**依赖倒置原则**（3 分）：高层 Report 直接依赖具体实现 OracleDao（依赖具体而非抽象），数据访问实现变化必然波及高层，且无法在测试中替换为轻量实现。

**【问题2】（8 分）**
方法一（边点公式）：V(G)＝E−N＋2＝9−8＋2＝**3**（3 分）；
方法二（判定节点法）：V(G)＝判定节点数＋1＝2＋1＝**3**（3 分），两种方法结果一致。
含义与阈值（2 分）：圈复杂度度量方法的**线性独立路径数**，是可测试性（至少需要 V(G) 个测试用例覆盖全路径）与可维护性的量化指标；行业经验阈值为 **10**，超过说明方法过长、分支过密，应拆分重构——本方法 V(G)＝3，复杂度健康。

**【问题3】（8 分）**
重构方案（4 分）：① 定义数据访问抽象接口 Dao（或 OrderRepository），声明 Report 所需的数据访问方法；② OracleDao、MySqlDao 等具体类实现该接口；③ Report 只依赖 Dao 抽象，具体实现通过**构造注入/设值注入**（依赖注入）由外部装配，不再出现 new 具体类。
满足的原则（2 分）：高层与低层均依赖 Dao 抽象＝**依赖倒置**；切换数据库只需提供新实现类并改装配配置，Report 代码零修改＝**开闭原则**。
可测试性提升（2 分）：单元测试可注入内存桩实现（StubDao）替代真实数据库，测试不再依赖环境、速度快且可精确构造边界数据——这正是"可测试性"质量属性在代码级的体现。

## 试题四（选答，25 分）

某企业办公审批系统采用 B/S 架构，团队就表现层设计展开讨论：一部分人主张直接在 JSP 页面中嵌写业务逻辑与数据库访问，另一部分人建议引入 MVC 框架分层组织。

**【问题1】**（8 分）说明 MVC 模式中 Model、View、Controller 三者的职责与协作关系，并指出观察者模式在 MVC 中的体现位置。
**【问题2】**（9 分）说明 MVC 与 MVP 的主要区别（从 View 与控制成分的关系、主动性、适用场景三方面比较）。
**【问题3】**（8 分）说明"三层架构（表示层-业务逻辑层-数据访问层）"与 MVC 的关系：二者是否冲突？企业审批系统应如何将两者结合？

## 试题四 参考答案

**【问题1】（8 分）**
职责与协作（6 分）：**Model**——封装业务数据与业务逻辑（状态与行为），不依赖视图与控制器；**View**——从 Model 获取数据并渲染展示给用户；**Controller**——接收用户输入（请求），调用 Model 完成业务处理，并选择/更新 View 展示。协作：用户请求→Controller→操作 Model→Model 状态变化→（通知）View 读取新状态并刷新→反馈用户。
观察者模式的体现（2 分）：Model 与 View 之间就是**观察者模式**——Model 是目标（Subject），一个 Model 可关联多个 View（观察者），Model 状态变化时自动通知全部注册的 View 更新，实现"一份数据、多视图同步"且 Model 不依赖具体视图。

**【问题2】（9 分）**
区别（每方面 3 分）：
- **与 View 的关系**：MVC 中 View 可直接从 Model 读取数据（Model-View 存在调用/订阅关系）；MVP 中 View 与 Model **完全隔离**，Presenter 持有 View 的抽象接口并主动调用 View 的方法渲染数据，一切通信经 Presenter 中转；
- **主动性**：MVC 的 View 具一定主动性（可观察 Model 自更新）；MVP 是**被动视图（Passive View）**，View 只提供 setter/渲染接口，不含逻辑，由 Presenter 驱动；
- **适用场景**：MVP 更便于对表现层做单元测试（Mock View 接口即可测 Presenter），适合界面复杂、测试要求高的桌面/表单密集型应用；MVC 框架生态成熟（Web MVC），适合请求-响应模式的 Web 应用。

**【问题3】（8 分）**
不冲突，二者是**正交的视角**（4 分）：MVC 是**表现层内部**的组织模式，解决"用户界面中数据、展示、输入处理"的分离；三层架构是**整个系统**的水平分层策略，解决"业务逻辑与数据访问"的分离。Controller 与 View 属于三层中的表示层，Model 的业务部分对应业务逻辑层、持久化部分对应数据访问层。
结合方式（4 分）：审批系统整体按三层划分——表示层内部采用 MVC（Controller 接收审批请求、调用业务层服务、选择视图渲染）；业务逻辑层实现审批流转规则；数据访问层封装表单与流程数据存取。即"宏观三层、表示层内 MVC"，两者叠加使用。

## 试题五（选答，25 分）

某电商平台需对退货流程建模。业务规则：买家提交退货申请后，客服在 4 小时内受理；受理后**技术检测与退款核算并行进行**；两者均完成且复核通过后执行退款并关闭退货单；任一环节不通过则退货单被拒绝；买家在客服受理前可随时取消申请。

**【问题1】**（9 分）为"退货单"绘制状态图（状态、事件、转换，覆盖取消与拒绝分支）。
**【问题2】**（9 分）为"受理后的处理"部分绘制活动图：用泳道区分客服、技术检测员、财务三个职责角色，用分叉/汇合表达"技术检测"与"退款核算"的并行，用判定表达"复核是否通过"。
**【问题3】**（7 分）说明状态图与活动图的选用原则，并回答：若要描述"多个对象在一次退货中的交互时序"，应选哪种 UML 图？

## 试题五 参考答案

**【问题1】（9 分）**

```
[已申请]──客服受理──▶[已受理]──并行处理启动──▶[处理中]──复核通过并完成退款──▶[已退款]──▶[关闭]
    │                    │                        │
 买家取消│                    │买家取消（4小时内）       │检测不通过/核算异常/复核不通过
    ▼                    ▼                        ▼
[已取消]              [已取消]                  [已拒绝]──通知买家──▶[关闭]
```
（状态 5 个：已申请、已受理、处理中、已退款、已取消/已拒绝、关闭，每个 1 分；事件（取消、受理、并行启动、复核结果、完成退款）与转换方向正确 4 分。等价画法均给分。）

**【问题2】（9 分）**
活动图要点（泳道 3 分、分叉/汇合 3 分、判定与汇合后流程 3 分）：

```
客服泳道：      受理退货单 ──▶ ──fork──▶ ‖并行走两条分支‖ ──join──▶ 复核 ──判定──通过──▶ 执行退款 ──▶ 关闭退货单
技术检测员泳道：                     └──▶ 技术检测 ──┘                └─不通过──▶ 生成拒绝单
财务泳道：                          └──▶ 退款核算 ──┘
```
- 三个泳道将活动按职责分区（谁做什么一目了然）；
- fork（粗横条）分出并行的"技术检测"与"退款核算"两个分支，join（粗横条）等两者**都完成**后才进入复核——表达同步并行；
- 复核后经判定（菱形）分支：通过→执行退款→关闭；不通过→拒绝。

**【问题3】（7 分）**
选用原则（5 分）：**状态图**描述**单个对象**在其生命周期内因事件触发的状态迁移，适合回答"这个对象会经历哪些状态"；**活动图**描述**跨角色的业务流程**，支持泳道、判定与并行分叉/汇合，适合回答"这个流程有哪些步骤、谁来做、哪些步骤同时进行"。判定标准看建模对象：一个对象的一生→状态图；一条流程的流转→活动图。
多对象交互时序（2 分）：应选**顺序图（时序图）**——按时间轴展示买家、退货界面、退货控制器、库存、支付等对象间的消息传递次序。
