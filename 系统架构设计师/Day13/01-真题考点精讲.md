## 二、核心考点精讲

### 考点 1：架构评估总论（目的、时机、角色）

**考点**：为什么评、何时评、谁来评。
**考法**：目的与时机判断题、参与角色辨析。
**速记**：
- 目的：**在系统实现之前**发现架构中的风险、敏感点与权衡点，**预测系统质量属性**，避免缺陷放大到实现阶段——评估不是证明架构完美，而是暴露风险；
- 时机：**架构基线确定后、大规模实现开始前**（最佳窗口）；架构在演化各里程碑**可以且应该多次评估**——评估不是一次性仪式；
- 参与角色三方：**评估组**（组织与方法执行）、**项目决策者**（架构师等项目方，回答问题、提供材料）、**干系人/涉众**（用户、运维、市场等，提供场景与判断）——评估绝不是开发人员的内部自查。

### 考点 2：质量属性场景与三类场景（评估的原材料）

**速记**：
- 质量属性场景**六要素**（Day09 复习）：**刺激源、刺激、环境、制品、响应、响应度量**——评估中一切场景必须改写成这个标准形态；
- 评估场景三分类：**用例场景**（用户正常使用系统的情形）、**生长场景**（系统预期**演化**的情形——新增功能、用户量增长、移植到新平台）、**探索场景**（**极端压力**情形——峰值流量、资源耗尽、多重故障同时发生）；
- 生长与探索是架构评估区别于需求评审的关键：它们专门**拷问架构对未来的承受力**。

### 考点 3：敏感点、权衡点、风险点、非风险点（案例必做送分）

**速记**（判定锚点）：
- **敏感点**：对**某一个**质量属性有显著影响的架构决策（"动这里，某属性会显著变"）；
- **权衡点**：影响**多个**质量属性且**相互制约**的决策（"动这里，此属性升彼属性降"）——权衡点是特殊的敏感点；
- **风险点**：经分析**可能造成质量隐患**的决策（"这里将来要出事"）；
- **非风险点**：经分析**确认无风险**的决策（"这里查过了，没问题"）——非风险同样要记录，它是已验证的好决策；
- 案例 30 秒判定法：先问"影响几个属性"（一个→敏感点，多个且制约→权衡点），再问"影响是好是坏"（隐患→风险点）。

### 考点 4：SAAM（最早的架构评估方法）

**考点**：SAAM 步骤与场景交互分析。
**速记**：
- 定位：**最早提出**的架构评估方法，简单、灵活，侧重**功能性与可修改性**分析，不深入多质量属性间的权衡；
- **六个步骤**：①**场景开发**（干系人提出场景）→②**架构描述**（补足场景驱动的视图）→③**场景分类**（**直接场景**：现有架构可直接支持；**间接场景**：需修改架构才能支持）→④**单独评估场景**（间接场景需估算修改成本）→⑤**评估场景交互**→⑥**形成总体评估**（加权结论）；
- **场景交互分析**是 SAAM 的独门兵器：两个场景（间接）**作用于同一构件**时产生交互——交互意味着**潜在的可修改性冲突**（一处变更牵动多处），是划分模块边界不合理的重要信号；
- 直接/间接场景比例本身就是结论：间接场景越多，架构对预期演化的支撑越弱。

### 考点 5：ATAM 九步法（绝对核心，必须能默写）

**速记**（九步三段式记忆）：

| 阶段 | 步骤 | 内容要点 |
|------|------|---------|
| 第一阶段（评估组与项目组） | 1 介绍 ATAM | 让各方理解方法本身 |
| | 2 商业动机 | 讲清业务目标、约束、最重要质量属性 |
| | 3 架构描述 | 架构视图、构件交互、明确所用架构方法 |
| | 4 识别架构方法 | 说出用了哪些风格/战术 |
| | 5 生成效用树 | 质量属性→细分→场景，双维度打分 |
| | 6 分析架构 | 针对高优先级场景找敏感点、权衡点 |
| 第二阶段（扩大干系人） | 7 头脑风暴定场景 | 全体干系人补充场景并**投票排序**（每人约 30% 场景数的选票） |
| | 8 再次分析架构 | 针对新场景重复步骤 6 |
| | 9 呈现结果 | 输出风险、非风险、敏感点、权衡点清单 |

- 三条主线贯穿：**场景驱动、效用树聚焦、决策分析**；
- 第一阶段"评估组＋项目组"小范围深挖，第二阶段引入**全体干系人**复核（步骤 7-9 的本质是防止效用树遗漏关键场景）；
- 步骤 6 的前提是架构描述充分——**架构说不清所用方法，评估就要停下来补文档**。

### 考点 6：效用树（ATAM 的聚焦装置）

**速记**：
- 结构：根节点"**效用**"→ 第二层**质量属性**（性能、可用性…）→ 第三层属性细分（如"数据丢失时""峰值负载时"）→ **叶节点＝具体场景**；
- 每个叶场景按**（重要性，实现难度）双维度**打分（H/M/L）——**（H,H）场景优先深入分析**；
- 作用：把 30 个场景收敛为 5-8 个"重要且难实现"的焦点，**保证评估的有限时间花在刀刃上**；
- 易错点：效用树的"效用"是质量属性对干系人的**价值**，不是功能清单——场景必须带响应度量。

### 考点 7：CBAM（架构决策的经济账）

**速记**：
- 定位：在 ATAM 输出（风险、权衡、候选改进）基础上，**用成本效益视角决定"做哪个改进"**——架构决策的经济学延伸；
- 核心思想：为每个改进方案估算**收益**（响应质量提升带来的价值，常折算为年化收益）与**成本**（实现成本），计算**投资回报**并排序；
- 常用指标：**投资回收期＝成本÷年化收益**、**ROI＝（收益−成本）÷成本**；
- 决策不是纯算术：还需做**风险调整**（不成熟技术收益打折）与战略权重（合规类必做）——CBAM 给出的是决策依据而非唯一答案。

### 考点 8：方法对比、选择与评估结果的运用

**速记**：

| 方法 | 焦点 | 适用 |
|------|------|------|
| SAAM | 功能+可修改性 | 时间紧、成熟度低的早期架构 |
| ATAM | 多质量属性权衡 | 大型关键系统、多方干系人 |
| CBAM | 成本效益 | 评估后决定改进投资排序 |

- 结果运用（高分点）：敏感点/权衡点记入**架构决策记录（ADR）**；风险清单纳入**项目里程碑跟踪**；评估结论驱动**架构文档补全**——评估输出不落文档等于白评；
- 补充：**ARID**（主动设计评审）适合对架构的**局部**（单个模块/接口）做渐进式评审，比 ATAM 轻；
- 常见误区（案例反选题）：评估开成功能演示会、只请开发人员、评估一次就束之高阁、把非风险点当浪费。
