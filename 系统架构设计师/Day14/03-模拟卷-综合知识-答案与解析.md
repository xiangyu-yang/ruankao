## 二、逐题解析（每题一答一析）

**1. B**【MVC组成】MVC＝Model（模型）＋View（视图）＋Controller（控制器），是交互式应用结构化的事实标准。

**2. C**【Controller职责】控制器接收请求、调用模型、选择视图——是"协调者"，业务规则在模型、展示在视图，控制器不越位。

**3. A**【Model职责】模型承载业务数据与业务逻辑，独立于展示方式——同一模型可服务多种视图。

**4. D**【View职责】视图负责向用户展示模型数据并支持交互；业务规则、数据库访问都不属于视图。

**5. B**【MVC优点】关注点分离是 MVC 的核心收益：逻辑、展示、控制解耦后可独立修改、并行开发与测试。

**6. A**【前后端分离】前端管展示交互、后端以 API 供数供能，接口契约协作、独立开发部署——"页面与数据各走各的"。

**7. C**【Web三层】业务逻辑层实现核心规则与流程：对上承接表现层、对下使用数据访问层——"规则与流程的家"。

**8. D**【ORM定义】ORM 把对象与关系表/行建立映射，操作对象即完成持久化，屏蔽 SQL 与方言差异。

**9. B**【ORM优点】提效率、可移植、防注入都是真实优点；"消除调优必要"是反题——复杂 SQL 场景 ORM 反而要手工干预。

**10. A**【ORM权衡】ORM 的代价是复杂查询的 SQL 可控性下降，报表、批量等极端场景仍需手写 SQL——开发效率换 SQL 精细控制力。

**11. C**【中间件定位】中间件位于操作系统与应用之间，提供通信、数据管理、事务等公共服务，屏蔽底层异构——"公共问题的产品化解"。

**12. D**【异步解耦】消息队列让生产者消费者时空解耦、削峰填谷，链路抗故障能力与水平扩展性显著提升。

**13. B**【削峰填谷】秒杀洪峰在队列中排队、消费端按可持续速率处理——用"排队"保住后端，这是消息队列的标志场景。

**14. A**【两种消息模型】点对点一条消息一个消费者；发布-订阅向主题发布、多订阅者各得一份——扩散 vs 独占之别。

**15. C**【投递语义】至少一次＝不丢但可能重复——重投不可避免，消费端幂等是标配而非可选项。

**16. D**【死信队列】死信队列收容多次失败/过期消息，防止一条"毒消息"堵死整条队列，并为后续处理保留现场。

**17. B**【积压处置】扩消费并行度、找慢因、必要时按优先级丢转——三步处置；清空队列等于丢业务。

**18. A**【顺序性保证】同业务键同分区、同分区同消费者顺序处理——全局有序代价太高，按需局部有序是工程正解。

**19. C**【负载均衡】负载均衡把请求按策略分发到多实例，避免单点过载并提升整体吞吐与可用性。

**20. D**【四层vs七层】四层按 IP/端口转发（快而粗），七层解析应用协议可按内容路由（强而贵）——"管流"与"懂内容"之分。

**21. B**【轮询】轮询顺序轮流分发、实现简单，适合实例能力相近的场景；能力不均时升级为加权轮询。

**22. A**【最少连接】请求时长差异大时，把新请求分给连接最少的实例更均衡——按"实时负载"而非"位置"分发。

**23. C**【源地址哈希】同源 IP 固定到同实例，无需集中会话即可简单保持——代价是负载可能不均。

**24. D**【健康检查】健康探测自动摘除故障实例、恢复再纳入——"流量不进死节点"是负载均衡可用的前提。

**25. B**【会话保持】推荐会话集中存储＋实例无状态化：任意实例可处理任意请求，弹性与故障切换才有意义。

**26. A**【分布式事务根源】一个业务跨多个服务与库，本地事务罩不住全部参与方——一致性与可用性的矛盾由此而来。

**27. C**【2PC特点】2PC 是强一致方案，但同步阻塞＋协调者单点使它在高并发长流程中代价高昂。

**28. D**【TCC思想】TCC 把两阶段上移到业务层：Try 预留资源、Confirm 确认、Cancel 释放——用业务补偿换弱化锁依赖。

**29. B**【Saga特点】Saga＝本地事务序列＋补偿，无全局锁、适合长流程，但中间状态对外可见——最终一致的典型代价。

**30. A**【本地消息表】业务与"待发消息"同一本地事务写入＋异步投递重试＋对账兜底——"业务成功则消息必达"的机制保证。

**31. C**【事务消息】半消息＋本地事务＋提交/回滚＋状态回查：以中间件内置机制解决"发消息与本地事务原子性"。

**32. D**【分布式事务选型】选型三问：一致性容忍度？流程多长？并发多大？——强一致核心用 2PC/TCC，可容忍最终一致的长流程用消息表/Saga。

**33. B**【反向代理】反向代理服务端前置：静态分发、负载均衡、SSL 卸载、安全防护——"门卫兼快递分拣"。

**34. A**【CDN】CDN 把静态资源放到离用户最近的边缘节点就近响应，降时延、卸源站——空间换时间。

**35. C**【动静分离】静态走 CDN/Nginx、动态走应用，各得其所互不拖累——一次分离两份收益。

**36. D**【分布式缓存】热点数据入内存，降库压、缩读延时；缓存是加速层不是持久层。

**37. B**【缓存穿透】查"不存在"的数据，缓存与库都不命中，请求全打库——空值缓存/布隆过滤器拦截。

**38. A**【缓存雪崩】大量 key 同时过期或缓存宕机是雪崩根源——过期时间随机打散＋多级缓存＋高可用集群三重防护。

**39. C**【缓存击穿】单个热点 key 失效瞬间请求全砸数据库——互斥重建/逻辑过期让"只有一个请求回源"。

**40. D**【缓存一致性】主流策略＝更新数据库后**删除**缓存（不更新缓存）＋过期兜底＋延迟双检——"删而非改"避免并发写乱序。

**41. A**【MIPS计算】MIPS＝2×10⁹÷(4×10⁶)＝500。（Day01 滚动复习）

**42. B**【可用度换算】99.999%＝五个 9：8760×0.000001 小时≈0.00876 小时≈5.26 分钟。（Day01 滚动复习）

**43. C**【缺页处理】缺页中断由操作系统缺页处理程序完成页面调度，对应用透明。（Day02 滚动复习）

**44. D**【3NF判定】消除部分依赖与传递依赖即 3NF；BCNF 还要求所有决定因素为超键。（Day02 滚动复习）

**45. A**【HTTPS端口】HTTPS 默认 443；80/21/53 分别是 HTTP/FTP 控制/DNS。（Day03 滚动复习）

**46. B**【子网计算】/26 主机位 6 位，可用主机数＝2⁶−2＝62。（Day03 滚动复习）

**47. C**【EDF】EDF 动态优先级、距截止期最近者优先；RM 是静态周期优先。（Day04 滚动复习）

**48. D**【硬实时】气囊超限即灾难性后果＝硬实时；丢帧仅影响体验的是软实时。（Day04 滚动复习）

**49. A**【2PC缺点】同步阻塞＋协调者单点是 2PC 的两大结构性缺陷。（Day05 滚动复习）
