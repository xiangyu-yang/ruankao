# Day14 模拟卷 · 科目二：案例分析（试题与参考答案）

> **本卷共 5 道大题，考生任选 3 道作答，其中第 1 题为必答题；第 2-5 题中任选 2 题。每题 25 分，建议限时 90 分钟。**

## 试题一（必答，25 分）

某游戏公司的在线竞技运营平台在赛季高峰频繁卡顿。已知：高峰期网关入口 QPS 峰值约 12000；单台应用服务器实例可稳定承载约 800 QPS；容量规范要求在峰值之上预留 25% 余量应对突发。当前架构为单体三层（表现/业务/数据），全部流量直连应用服务器，无缓存层；前端静态资源（皮肤、音效、活动页）与应用接口同源同服务器。公司要求你重构高并发 Web 架构。

**【问题1】**（9 分）计算满足容量要求的应用实例数量（写出计算过程并说明取整原则）；结合请求时长差异，说明负载均衡算法在轮询与最少连接之间如何选择。
**【问题2】**（8 分）给出"动静分离＋CDN＋反向代理＋分布式缓存"的整体架构设计，说明各组件分担的压力。
**【问题3】**（8 分）活动皮肤上线瞬间出现过"热门皮肤详情接口数据库被打满"，分析该现象属于缓存穿透、击穿还是雪崩，并给出完整的防护方案。

## 试题一 参考答案

**【问题1】（9 分）**
实例数计算（6 分）：基准实例数＝12000÷800＝15；含余量＝15×1.25＝18.75，向上取整＝**19 个实例**（写出公式 3 分＋计算与取整 3 分——余量必须向上取整，19 个；若答 18.75 个实例属于未完成计算）。
算法选择（3 分）：游戏运营平台请求时长差异大（查询快、对局结算与排行榜计算慢），轮询可能把慢请求集中到个别实例造成倾斜——应选**最少连接**（或加权轮询兼顾实例能力差异），把新请求分给当前连接最少的实例，实现更均衡的动态分发（答轮询＋说明权重修正可酌情给一半）。

**【问题2】（8 分）**
（每个组件"做法＋减压对象"各 2 分）**动静分离**：静态资源（皮肤/音效/活动页）与动态接口分轨——静态不再占用应用服务器；**CDN**：静态资源上 CDN 边缘节点，用户就近获取，回源流量大幅下降；**反向代理**：入口前置 Nginx 类代理，做 SSL 卸载、Gzip 压缩、限流与负载均衡，静态小文件直接代理返回；**分布式缓存**：排行榜、段位、热门活动等热点读全部走内存缓存（命中率目标 95%＋），数据库只承接未命中的回源与写入。四层过滤后，到达数据库的请求量通常可下降一个数量级。

**【问题3】（8 分）**
现象判断（3 分）："热门皮肤详情"是**单一热点 key**（该皮肤详情缓存），上新瞬间该 key 失效/未预热，海量请求同时打到数据库——属于**缓存击穿**（穿透是查不存在的数据；雪崩是大量 key 同时失效）。
防护方案（5 分，每条 1-2 分）：① **互斥重建**：该 key 失效时仅允许一个请求回源数据库重建，其余请求短暂等待或返回旧值；② **逻辑过期**：热点 key 不设物理过期，值内含逻辑过期时间，由异步线程刷新，请求永不直接击穿到库；③ **预热**：活动上线前主动把皮肤详情加载入缓存；④ **热点 key 多级缓存**（本地缓存＋分布式缓存）；⑤ 前置限流兜底。

## 试题二（选答，25 分）

某快递物流集团的运单跟踪平台每天产生 2 亿条轨迹事件（司机 App 上报 GPS、扫描、签收事件）。轨迹事件先入消息队列再由处理服务落库与推送。近期两类问题：①个别运单的轨迹顺序错乱（后扫描先显示）；②一次消费服务 Bug 导致消息批量消费失败，队列大量积压，期间轨迹查询滞后 3 小时；③上游重试曾造成同一扫描事件被重复落库。

**【问题1】**（8 分）分析轨迹顺序错乱的原因，给出按运单号保证消息顺序的处理方案。
**【问题2】**（9 分）针对消费失败与积压：说明死信队列的处置流程，以及积压恢复的综合措施（至少三条）。
**【问题3】**（8 分）给出消费端幂等方案，杜绝重复落库；并说明轨迹查询侧如何容忍消费延迟。

## 试题二 参考答案

**【问题1】（8 分）**
原因（3 分）：多队列/多消费者并发处理，同一运单的多条事件被分散到不同分区并行消费，完成顺序与产生顺序不一致。方案（5 分）：以**运单号作为分区键**路由消息——同一运单的事件必然进入同一分区、由同一消费者线程顺序消费；消费失败时在分区内原地重试，避免乱序；跨运单不要求全局有序（说明"局部有序即可"）。

**【问题2】（9 分）**
死信流程（4 分）：消息消费重试达到次数上限（如 16 次）仍失败→转入**死信队列**→不再阻塞正常队列→死信由独立服务或人工分析处理（Bug 修复后回放）；本次 Bug 场景的正确处置是：修复 Bug→扩容消费实例快速消化积压→回放死信补数据。
积压恢复措施（5 分，每条约 1.7 分）：①水平扩容消费者（分区内并行受限时可临时增加分区与消费者，回放后恢复）；②定位并修复消费瓶颈（批量写入、慢 SQL）；③非关键消息（如重复 GPS 点）按采样/丢弃策略降级；④积压期间轨迹查询走"最近已知位置"降级视图；⑤建立积压水位告警，早于业务感知。

**【问题3】（8 分）**
幂等方案（5 分）：为每个扫描/签收事件生成全局唯一事件 ID（或运单号＋事件类型＋时间戳指纹），落库表以事件 ID 建**唯一约束**；消费前查"已处理表"（或将写入放入"INSERT IGNORE/ON CONFLICT"式幂等写），重复消息直接跳过——重复投递不产生重复行。
查询侧容忍（3 分）：轨迹查询接口返回"位置更新时间"并标注"数据存在分钟级延迟"；关键节点（签收、异常）由独立实时通道推送保证时效，普通轨迹允许延迟刷新。

## 试题三（选答，25 分）

某在线差旅平台的"自由行套餐"下单链路涉及三个独立服务：机票服务（出票）、酒店服务（锁房）、保险服务（投保）。业务规则：三者要么全部成功，要么全部撤销；其中保险可以接受"晚 10 分钟生效"，但机票与酒店必须同步确认，否则用户可能"付了钱没有房"。团队在 2PC、TCC、本地消息表三种方案间犹豫。

**【问题1】**（9 分）对比三种方案在本场景的适配性，说明你的选型及理由。
**【问题2】**（8 分）给出所选方案的详细设计：以机票-酒店为主线说明各阶段动作与失败补偿。
**【问题3】**（8 分）说明消费者（保险服务）侧的幂等与对账设计。

## 试题三 参考答案

**【问题1】（9 分）**
2PC（3 分）：强一致但同步阻塞、协调者单点，跨服务长流程（出票可能数十秒）持锁代价过高——排除；
TCC（4 分）：机票与酒店是"必须同步确认"的强一致核心链路——Try 阶段完成占座/锁房（冻结），Confirm 立即出票/确认锁房，Cancel 释放；业务侵入大但时延可控、无中间对用户裸露，适配核心段；
本地消息表（2 分）：保险可容忍 10 分钟延迟——出消息走异步最终一致即可，不必纳入强一致段。
选型结论：**核心链路（机票＋酒店）用 TCC，保险用本地消息表异步补齐**——按一致性容忍度分段选型。

**【问题2】（8 分）**
TCC 设计（每阶段约 2-3 分）：Try：冻结用户支付额度，机票服务锁定座位、酒店服务锁定房量（均为"预留"不落地）；两处 Try 均成功→Confirm：依次（可并行）正式出票、确认锁房、扣款落地；任一 Try 失败→Cancel：逆向释放全部已成功的 Try 预留（机票 Cancel 释放座位、酒店 Cancel 释放房量、支付解冻）。补偿要点：Cancel 幂等（可能重复调用）；Confirm 失败的极端场景必须有重试与人工兜底通道（出票失败触发退款流程）。

**【问题3】（8 分）**
幂等（4 分）：保险服务消费"套餐已成立"事件时，以套餐订单号为唯一键，落库唯一约束＋已处理消息表，重复消息直接跳过；投保结果回执事件同样幂等。
对账（4 分）：每小时比对"套餐订单表"与"保险保单表"，缺失保单的订单触发消息重投或生成补投任务；连续失败进人工队列；对账是最终一致的最终防线，必须独立于消息链路运行。

## 试题四（选答，25 分）

某连锁便利店集团的会员系统是五年前的单体：Controller 里直接拼 SQL 访问数据库并拼 HTML 返回（既当控制器又当数据访问层）；新上线的"会员权益报表"用 ORM 逐条查询 500 万会员的最近消费，代码循环加载每个会员的订单集合，上线当天把数据库拖垮。团队决定重构。

**【问题1】**（9 分）指出当前实现违反的分层/职责原则，给出重构后的三层职责划分（结合 MVC 说明）。
**【问题2】**（10 分）分析 ORM 循环加载性能问题的成因（N+1 查询），给出至少三种修复手段并说明适用性。
**【问题3】**（6 分）说明重构后如何保证"表现层不再直接访问数据库"的规则长期有效。

## 试题四 参考答案

**【问题1】（9 分）**
违规点（5 分）：Controller 同时承担请求控制、数据访问、视图渲染三种职责——违反 MVC 关注点分离与分层原则（表现层直连数据库）；任何一处修改牵动全局、无法独立测试。重构（4 分）：Controller 只做请求接收与视图选择；业务规则全部下沉到业务逻辑层（会员、积分、权益规则）；数据库访问统一收敛到数据访问层（ORM 实体与仓储），表现层禁止直连数据库；视图由模板渲染，与控制解耦。

**【问题2】（10 分）**
成因（4 分）：代码中"取会员列表（1 次查询）＋循环内取每个会员的订单（N 次查询）"——ORM 惰性加载触发 **N+1 查询**：500 万会员即 500 万＋次 SQL，数据库被打垮。
修复手段（6 分，每条约 2 分）：① 批量查询＋内存关联：一次性按会员 ID 集合取订单再组装（最直接）；② ORM 的**连接抓取/立即加载**配置（join fetch）一次性取回关联数据——适合关联层级浅的场景；③ 报表类海量统计改走**分析库/列存**或 SQL 聚合直接出数，不走 ORM 实体——大报表本就不该逐行加载对象；④ 分页/流式分批处理控制单次规模。说明适用性：日常接口用②③，离线报表用③④。

**【问题3】（6 分）**
（每条 2 分，答满三条）① **静态检查门禁**：在 CI 流水线加架构守护规则（如禁止表现层包引用数据访问包/驱动类），违规构建失败；② **评审纪律**：数据访问只能经由业务层→仓储接口，架构评审抽查分层依赖；③ 工具上使"绕过"变难：数据库账号只授权给数据访问层所部署的模块/连接池配置，表现层无法获得连接凭据（答出"机制化守护"思想即可）。

## 试题五（选答，25 分）

某智慧停车场运营商平台故障复盘：周一早高峰，商场推出"全场停车五折"活动，大量用户同时查询"我的停车账单"，账单服务数据库 CPU 打满，接口超时；同时门口道闸的车牌识别结果上传队列积压 20 分钟，道闸放行延迟被车主投诉。事后排查发现：①活动折扣键的缓存在活动开始时被设计为"整点集中过期"；②账单接口存在按"车牌号+不存在的时间段"恶意查询的日志记录；③车牌识别上传消费服务在故障期间持续重试写库失败。

**【问题1】**（9 分）分别判断①②对应的缓存问题类型（雪崩/穿透/击穿），并给出针对性防护。
**【问题2】**（8 分）针对道闸上传队列积压与消费服务反复失败，给出死信处理与恢复设计。
**【问题3】**（8 分）从缓存设计、消息链路、降级预案三个角度给出防止此类早高峰故障复发的综合方案。

## 试题五 参考答案

**【问题1】（9 分）**
①活动折扣键"整点集中过期"→大量键同时失效、请求集中打到数据库，属于**缓存雪崩**（3 分）；防护（2 分）：过期时间加随机打散、活动键预热且采用逻辑过期/异步刷新、多级缓存与高可用缓存集群。
②"车牌号＋不存在的时间段"恶意查询→缓存与数据库都不命中，属于**缓存穿透**（2 分）；防护（2 分）：对不存在的键做**空值缓存**（短 TTL）、入口参数校验（时间段合法性）、布隆过滤器拦截非法键、限流。
（说明击穿为单个热点 key 失效、本题不适用者加分。）

**【问题2】（8 分）**
死信设计（4 分）：消费重试达到上限（如 10 次）→转死信队列→原队列不再被失败消息阻塞；死信由独立程序定期分析，可修复后回放（车牌上传属不可再生数据，必须入死信而非丢弃）；恢复流程（4 分）：修复写库故障→扩容消费者实例消化积压→回放死信补数据→对账核对道闸流水与平台账单一致；积压期间道闸按"本地缓存的白名单＋计费兜底"先放行、后补账。

**【问题3】（8 分）**
（每方面 2-3 分）缓存设计（3 分）：活动类热点键一律预热＋逻辑过期，禁止整点集中失效；空值缓存与参数校验防穿透；容量按 3 倍峰值规划；
消息链路（2-3 分）：消费端幂等（车牌＋时间戳唯一键）保证重试安全；水位告警分级（积压 1 分钟/5 分钟两级响应预案）；
降级预案（2-3 分）：早高峰"读走缓存快照、写走异步补录"的降级模式，道闸放行永不依赖平台数据库可用性（本地自治）；预案每季度演练一次。
