## 二、核心考点精讲

### 考点 1：读写分离（读扩展的第一步）

**考点**：主从复制原理、复制延迟与对策、切换与脑裂。
**速记**：
- 原理：**写固定走主库，读分发到从库**，主库以**日志（binlog）复制**同步从库——多数为**异步复制**；
- 适用：**读多写少**、读可容忍毫秒到秒级延迟的业务；
- **复制延迟**的经典症状＝"写后立读读不到"（读到旧从库）；对策＝**关键写后读强制路由主库**、会话粘主、按位点/延迟路由到已追平从库；
- **半同步复制**：主库提交等至少一个从库确认收到日志——缩小丢失窗口、平衡性能；
- **主从切换**：故障检测→提升数据最新从库为新主→写流量重定向；**防脑裂＝第三方仲裁/多数派投票**，只允许一方持写权。

### 考点 2：分库分表（拆的艺术）

**速记**：
- 触发条件：**单表行数过大（数亿级）或单库写入/连接压力超限**；
- **垂直分库**＝按业务域拆（订单库/商品库/用户库）；**垂直分表**＝按列拆（大字段、低频字段分离）；**水平分（拆）表**＝按规则把行分散到多个分片（结构同、数据不同）；
- **拆分键原则**：选最高频查询维度中的业务主键（如用户 ID），让多数查询**单分片命中**；
- 分片算法对比（高频）：

| 算法 | 优点 | 缺点 |
|------|------|------|
| 哈希取模 | 分布均匀 | **扩容几乎全量 rehash** |
| 时间范围 | 利于冷热分离与归档 | 写入集中最新分片→热点 |
| 一致性哈希 | 扩容只迁移邻近环段 | 实现较复杂 |

- **基因法**：把分片键后缀嵌入另一业务键（订单号尾号含买家 ID 尾号）——双维度都能路由到同一分片；
- 拆分的新问题（年年考）：**跨库 join/聚合困难**（归并、异构宽表）、**跨库深分页**（各分片取 N 行归并/游标）、**全局唯一 ID**（自增不可用→**号段/雪花**）、跨库事务（最终一致）。

### 考点 3：缓存架构（读的性能倍增器）

**速记**：
- **Cache-Aside（旁路缓存）**：应用先查缓存→未命中查库并**回填**→更新时**先更新库再删除缓存**；
- **Read-Through**：缓存层自己负责加载回源，应用只感知缓存（与 Cache-Aside 的分工差别）；
- 更新顺序主流实践：**先库后删缓存＋过期兜底＋延迟双删**（"删而非改"防并发乱序）；
- **预热**：高峰前主动加载热点，防冷启动击穿；**多级缓存**（本地＋分布式）：本地需失效广播/短 TTL 防不一致；
- **超级热点 key**：本地内存承载或 key 分片打散；**LRU**＝淘汰最近最久未使用；
- **命中率**＝缓存层卸载效果的直接指标，骤降是穿透/容量不足的前兆。

### 考点 4：CAP 与 BASE（选型论证的理论根）

**速记**：
- **CAP**＝一致性、可用性、**分区容忍**；分区客观不可避（P 必留），故实际在 **C 与 A 之间取舍**：账务/库存强一致选 **CP**（宁可拒绝服务），内容/社交体验优先选 **AP**（最终一致）；
- **BASE**＝**基本可用＋软状态＋最终一致**——AP 路线的工程化表达；最终一致＝不保证任意时刻一致，但保证无新更新时经一定时间后收敛一致；
- **共识协议（Paxos/Raft）**：多数派就变更达成一致——副本强一致与主选举的理论基础；
- 记忆链：CAP 定方向 → BASE 给承诺 → 共识协议做实现。

### 考点 5：NewSQL 与分布式数据库（近年新考点）

**速记**：
- **NewSQL 核心特征**＝兼容**关系模型与 SQL**＋**分布式水平扩展**＋保持 **ACID 强一致**——"既要 SQL 的好，又要分片的快"；
- **NewSQL vs 分库分表中间件**：前者把分片、路由、副本、分布式事务做进**数据库内核层**，应用近乎**透明**；后者由应用/中间件层承担数据分布细节；
- **NewSQL vs NoSQL**：NewSQL 是关系模型与强事务的回归；NoSQL 以放松关系与一致性换特定场景的灵活与性能；
- 副本与分片：数据按分片规则散布、每分片多副本（多数派共识保一致）。

### 考点 6：数据库高可用与容灾度量

**速记**：
- **RTO**＝恢复时间目标（中断→恢复服务的时长）；**RPO**＝恢复点目标（可容忍的最大数据丢失时间窗）——容灾能力的两把尺；
- **同城双活**：两数据中心同时承载业务、互为备份——任一中心故障快速接管，容灾与资源利用率双收；异地灾备解决区域级灾难（RTO/RPO 更长）。
