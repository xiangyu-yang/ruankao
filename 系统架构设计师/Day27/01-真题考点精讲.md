# Day27｜系统架构设计师｜论文日三：专项与新技术论文——结构解剖＋范文精读（进阶）

> **Day27 定位**：收官周第三个论文专项日。总计划本日主题为"论数据库架构／论大数据架构／论遗留系统改造"等专项与新技术类论文的范文精读。此类题与 Day25 的"架构风格应用"共用一副骨架，但审题更险：**专项题考纵深**（一道题吃透一个技术域），**新技术题考架构判断**（不炫技、讲取舍）。本卷两道论文题按第二轮规则复现：数据库设计与性能优化（索引与执行计划主线）、SOA（服务资产化与 API 治理主线）。

---

## 一、专项/新技术类论文的三个审题陷阱

1. **陷阱一：把专项论文写成产品说明书**。通篇罗列技术特性（索引类型大全）而没有"我的系统为什么这么选"——专项题的采分点在**论证链**（现象→原因→方案→效果），不在名词密度。
2. **陷阱二：把新技术论文写成跟风檄文**。"引入大模型/区块链一步到位"式叙述暴露判断力缺失；新技术题要写**适用性论证**（解决什么、不解决什么、代价是什么、何时不用它）。
3. **陷阱三：忽视"演进性"叙事**。专项优化几乎都有"优化前→定位→优化后"的时间线，把优化过程写成一次性成功会失真；**写定位过程**（怎么发现慢、怎么归因）恰是架构师的看点。

## 二、专项类论文的"论点三段式"升级模板

每个论点内部从 Day25 的四步（理论→方案→取舍→效果）升级为**五步闭环**：

> **现象与量化 → 归因与理论 → 方案与对比 → 实施与代价 → 效果与验证**

以数据库优化为例：慢查询 P95 3.8 秒（现象量化）→ EXPLAIN 显示全表扫描＋索引失效（归因，引用理论：最左前缀/区分度）→ 建联合索引 vs 改 SQL vs 引缓存（对比取舍）→ 索引带来的写入放大代价与解决（代价）→ P95 降至 210ms 且写入 RT 只增 3ms（验证）。

**范文精读刀法（在 Day25 四步基础上加一步）**：拆骨架→拆数字→拆术语→**拆归因链**（作者如何从现象走到原因）→换皮重写。归因链是专项论文的灵魂，抄不来的正是这一段。

## 三、本卷两道新题的审题与理论词表

### 3.1 试题一：论数据库设计与性能优化（第二轮：索引与执行计划优化为主线）
- **与第一轮的区别**：D02-1 写"设计过程全景"（建模→范式→评审），D20-1 写"建模与反范式"；本轮聚焦**运行期优化**——执行计划、索引、SQL 治理，设计只作铺垫一句话。
- **理论词表**：执行计划（EXPLAIN，type 从 const/ref/range/index 到 ALL 的劣化阶梯）、索引失效五场景（对索引列做函数运算、隐式类型转换、前导模糊 LIKE '%x'、OR 连接非索引列、违反最左前缀）、联合索引与最左前缀、覆盖索引（免回表）、区分度与索引选择性、慢查询日志与治理闭环（采集→评审→优化→回归）、事务与锁对并发的影响。
- **数字建议**：慢查询条数/耗时前后对比、索引数量、写入放大代价、容量与增长率。
- **背景建议**：有"读多写少＋偶发写入洪峰"特征的调度/工单/订单类系统最易展开。

### 3.2 试题二：论面向服务的架构 SOA（第二轮：服务资产化与 API 治理为主线）
- **与第一轮的区别**：D07-2 写的是"ESB 集成与选型"；本轮聚焦**服务作为资产管理**——服务识别与资产库、API 生命周期、开放平台运营。ESB 只作为历史包袱或现状出现。
- **理论词表**：服务识别（自顶向下业务分解＋自底向上系统盘点）、服务资产库（注册、分级分类、检索）、API 生命周期（设计→评审→发布→版本→废弃下线）、契约（接口契约与版本兼容）、API 网关（鉴权、限流、监控）、开放平台（配额、安全、运营度量）。
- **数字建议**：整合前接口数/系统数、服务资产项数、新应用接入周期前后对比、API 复用率、开放渠道规模。
- **背景建议**：多系统林立、渠道众多的集团型企业（制造、商贸）最典型。
