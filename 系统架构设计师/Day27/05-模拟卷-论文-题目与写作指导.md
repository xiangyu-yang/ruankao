## 试题一：论数据库设计与性能优化（第二轮：以索引与执行计划优化为主线）

### 题目要求
数据库是信息系统的核心资产，其性能直接决定系统服务质量。随着业务量增长，数据库性能优化往往成为架构师必须面对的挑战。请围绕"数据库运行期性能优化"论你的实践：
1. 概述项目背景、你的角色与数据库面临的性能问题（须有量化描述）；
2. 详细论述执行计划在慢查询定位中的应用（如何解读、如何归因）；
3. 详细论述索引设计与索引失效治理（联合索引、覆盖索引的设计原则，典型失效场景的识别与改造）；
4. 详细论述 SQL 治理与慢查询闭环（上线前拦截、慢日志闭环、写入代价的权衡）；
5. 最后给出优化成效（前后对比数据），并分析不足与体会。

### 写作指导
- **与第一轮的区别**：D02-1 论"设计过程全景"、D20-1 论"建模与反范式"——两者都是**设计期**；本轮聚焦**运行期优化**：执行计划→索引→SQL 治理的完整方法论，与设计期内容明显区隔（间隔 23 天达标）；
- **理论词表**：EXPLAIN 与 type 阶梯（const/ref/range/index/ALL）、回表与覆盖索引、最左前缀、索引选择性、失效四场景（函数/隐式转换/前导模糊/低选择性）、写入放大、慢查询闭环（采集→评审→优化→回归）；
- **结构建议**：摘要 300 → 概述与问题量化 400 → 执行计划与定位 550 → 索引设计与失效治理 550 → SQL 治理闭环 450 → 成效与"不足与体会"300；

### 参考范文（约 2500 字）

**摘要**
2025 年 3 月，我所在公司启动"巡检业务支撑平台数据库性能优化"专项，本人担任系统架构师，负责优化方案总体设计与实施。我司为无人机巡检服务公司，业务覆盖全国 26 省，年巡检 3.2 万架次、采集巡检影像 900TB。平台核心的工单调度与影像元数据数据库已积累 5.8 亿行数据，业务高峰期慢查询日均 1200 条，工单派发接口 P95 延迟达 3.8 秒，多次触发派单超时告警。我以执行计划为定位主线，解读慢查询的访问路径与失效原因；以联合索引与覆盖索引重构查询路径，治理函数运算、隐式转换、前导模糊等典型失效场景；并建设 SQL 审核平台实现"上线前拦截"，配套慢日志形成"采集—评审—优化—回归"闭环。经四个月实施，工单接口 P95 延迟降至 210 毫秒，慢查询降至日均 30 条，全表扫描清零，写入延迟仅增加 3 毫秒，原计划的服务器扩容取消、节省投资约 240 万元。本文从执行计划定位、索引治理、SQL 闭环三方面论述该实践。

**一、项目背景与问题量化**
无人机巡检业务的典型特征是"影像海量、工单高频"：每次巡检产生 2000-8000 张航拍影像，元数据（拍摄坐标、时段、缺陷标记、所属工单）写入工单库；电网客户要求巡检报告 48 小时内交付，报告生成与工单派发叠加形成晚高峰。2025 年初平台数据库告警密集：影像元数据表 5.8 亿行、日增 160 万行；慢查询日志（阈值 1 秒）日均 1200 条；工单派发接口晚高峰 P95 延迟 3.8 秒，超时率 2.3%，一线调度员被迫手工重派。更棘手的是，团队此前形成了"一慢就加索引、越加越乱"的恶性循环——该表已堆积 11 个单列索引，写入延迟同步恶化。专项组由我担任系统架构师，投资 560 万元、计划 7 个月。我的第一判断是：优化的前提是定位，定位的工具是执行计划——不能再"凭感觉加索引"。

**二、以执行计划为线索的慢查询定位**
专项第一步是全员培训"读执行计划"。我们统一用 EXPLAIN 输出三个关键信息：type（访问方式，从 const、ref、range 逐级劣化到 index、ALL）、rows（预估扫描行数）、Extra（Using index 表示覆盖索引免回表，Using filesort 与 Using temporary 则警示排序与临时表开销）。定位中发现一个典型案例：工单列表查询预估扫描行数高达 2.3 亿，与实际返回的 300 行严重失配——这不是索引缺失，而是统计信息过期导致优化器误判，先执行 ANALYZE TABLE 更新统计即消除了两成"假慢"。对真正的慢查询，我们按归因分成四类建立台账：函数失效类（对拍摄时间列套 DATE 函数）、隐式转换类（工单号 VARCHAR 列与数字比较）、低选择性类（状态列仅 2 个取值）、联合索引误用类（违反最左前缀）。台账每周复盘，归因不清的案例由我组织"执行计划阅读会"现场推演——把"优化"从玄学变成"看图说话"，这是本阶段最重要的能力建设。

**三、索引设计与失效治理**
索引治理遵循"先理需求、再定索引"的原则。最高频的查询是"按客户查某时间段工单"，我们设计联合索引 (customer_id, shot_time)：customer_id 等值过滤命中最左列、shot_time 范围条件紧随其后，一次树定位即可圈定区间；反之若以 (shot_time, customer_id) 为序，范围条件占住最左列后，customer_id 只能在区间内逐行过滤——"等值在前、范围在后"是联合索引列序的第一原则。对影像列表页，我们把查询所需的七个列全部纳入二级索引形成覆盖索引，EXPLAIN 的 Extra 显示 Using index，查询不再回表，P95 从 1.6 秒降至 90 毫秒。失效治理同步推进：函数失效改造为范围条件写法（时间下界与上界代替 DATE()）；隐式转换在应用层统一参数类型规范并加 SQL 审核规则拦截；前导模糊 LIKE 改为搜索服务承担；低选择性状态列一律不再单独建索引，只作为联合索引的后缀列。原有 11 个单列索引经使用率审计后保留 3 个、下线 8 个——索引不是越多越好，而是"每个索引都要有它服务的查询"。

**四、SQL 治理与慢查询闭环**
运行期治理之外，我坚持把问题拦在上线之前。我们引入 SQL 审核平台，对发布流程做硬约束：所有 SQL 变更（新表、新索引、新查询语句）必须经平台自动校验——是否含全表扫描风险、是否缺失索引建议、是否存在已知失效写法，高危规则直接阻断发布。灰度上线的查询同步纳入慢日志监控（阈值 1 秒），形成"上线前拦截＋上线后观测"双闸。慢查询闭环按周运转：采集（慢日志）→评审（DBA 与开发联合归因）→优化（改写或建索引，遵循本文第三部分原则）→回归（同语句执行计划与耗时复测）→归档（进入反模式案例库）。索引新增的写入代价我们做了显式度量：联合索引方案使影像写入平均延迟增加 3 毫秒（从 12 到 15 毫秒），仍在业务容忍内；而下线 8 个冗余索引反而使批量导入提速 18%——治理是双向的加减法，不是单边堆砌。

**五、成效、不足与体会**
四个月集中治理加两个月巩固，最终指标：工单派发接口 P95 由 3.8 秒降至 210 毫秒，超时率从 2.3% 降至 0.02%；慢查询由日均 1200 条降至 30 条；全表扫描清零；原定的存储与服务器扩容方案取消，节省约 240 万元。不足亦有三点：其一，审核平台规则误报率约 15%，需要人工复核，规则引擎的准确率仍有优化空间；其二，统计信息依赖人工触发更新，两次统计过期引发"假慢"告警，自动化的统计巡检应尽早建设；其三，反模式案例库初期靠个人沉淀，后来才配套了评审会机制——知识管理总是落后于技术动作，这是组织能力的常态短板。我的体会是：数据库性能优化的方法论核心是"先定位后动手"——执行计划把不可见的查询行为变成可读的证据链，索引设计是把高频查询模式翻译成树形数据结构，而 SQL 治理是把个体经验固化为流程闸门。三者环环相扣，缺了定位是瞎治，缺了治理是反复发作——架构师的价值在于让系统从"靠人救火"走向"按机制运转"。

## 试题二：论面向服务的架构 SOA（第二轮：以服务资产化与 API 治理为主线）

### 题目要求
面向服务的架构（SOA）将系统能力封装为可复用的服务。当企业服务数量增长后，服务能否被当作"资产"管理与运营，决定 SOA 的长期成效。请围绕"服务资产化与 API 治理"论你的实践：
1. 概述项目背景、你的角色与原集成架构存在的问题；
2. 详细论述服务识别（自顶向下与自底向上）与企业服务资产库的建设；
3. 详细论述 API 生命周期治理（设计、评审、发布、版本、下线）；
4. 详细论述面向外部伙伴的开放平台运营实践；
5. 最后给出项目成效，并分析不足与体会。

### 写作指导
- **与第一轮的区别**：D07-2 的主线是"ESB 与集成选型"（一次集成工程）；本轮主线是**服务作为资产的长期治理与运营**——服务识别、资产库、API 生命周期、开放平台，ESB 只作为历史现状出现（间隔 20 天达标）；
- **理论词表**：自顶向下业务能力分解、自底向上功能盘点、服务资产库（注册/分级分类/检索/复用统计）、契约先行、契约测试、API 版本兼容（只加不破）、配额管理、AppKey/HMAC 签名、复用率；
- **结构建议**：摘要 300 → 概述 400 → 服务识别与资产库 550 → API 生命周期 550 → 开放平台运营 450 → 成效与"不足与体会"300；
- **数字建议**：整合前系统数与接口数、服务资产项数、新应用接入周期前后对比、复用率、开放渠道规模与在线订单占比。

### 参考范文（约 2500 字）

**摘要**
2024 年 5 月，我所在的某乐器制造集团启动"企业服务资产化与开放平台"建设项目，本人担任系统架构师，负责总体架构设计。集团旗下钢琴与民乐两大事业部、6 大生产基地、经销商 2200 家，运行 ERP、MES、CRM、渠道、售后、物流、财务等 14 套系统，两两之间堆叠出 217 个点对点接口：口径不一、重复建设，一端变更全网告警，新应用接入平均耗时 6 周。项目中，我以"自顶向下业务分解＋自底向上系统盘点"双向识别出 130 项企业服务并建成服务资产库（注册、分级分类、检索、复用统计）；建立 API 生命周期治理（契约先行、评审、灰度发布、版本兼容、废弃下线）并以契约测试防回归；建成面向 2200 家经销商的开放平台，配套配额管理与签名鉴权安全体系。项目上线后，新应用集成周期从 6 周缩短至 5 天，API 复用率达 68%，经销商在线订单占比升至 92%，集成类故障下降 74%。本文从服务识别与资产库、API 生命周期、开放平台运营三方面论述该实践。

**一、项目背景与我的角色**
乐器制造的行业特点在信息化上体现为"多品类、长渠道、强定制"：钢琴与民乐事业部业务规则差异大，但共用集团级经销商、仓储与结算；2200 家经销商中有近半兼营两大品类，此前需要在两套渠道系统分别下单。多年建设留下 14 套系统、217 个点对点接口：同一个"经销商可用额度"逻辑被四套系统各自实现，口径已经有两处不一致引发过对账纠纷；ERP 升级一次，相关六个系统联调两周。2024 年 5 月集团立项，投资 1300 万元、工期 14 个月，我担任系统架构师。我在方案评审时明确：本项目不是"再建一个集成平台"，而是"把接口变成资产、把集成变成治理"——重点是让服务可识别、可检索、可复用、可运营，而不是引入一个新的技术组件把旧问题包一层。

**二、服务识别与资产库建设**
服务识别我坚持"双向对齐"。自顶向下：以业务能力地图为骨架，从"经销商管理、订单履约、库存与批次、结算对账"四大能力域向下分解，产出候选服务清单，保证服务与业务对齐；自底向上：盘点 14 套系统现有 217 个接口，按语义聚类去重（例如四套系统里的"额度查询"归并为一项）。两向结果做映射对齐，暴露出两类问题："业务需要但系统没有"（如跨品类统一订单服务，列新建）与"系统有但业务未用"（如三套遗留报表接口，列下线候选）。最终收敛出 130 项服务，全部纳入服务资产库：每项服务注册契约文档、业务域、责任人、SLA 承诺与版本状态；按核心（结算、订单履约）、重要（库存、额度）、一般（查询类）三级分类，核心服务匹配 99.95% 可用性目标与分钟级监控告警，一般服务从简——治理资源按级别分配，避免"平均主义"。资产库对全员开放检索门户，按业务域与关键词即可找到"该复用什么、找谁对接"。没有资产库之前，复用靠口口相传；有了它，复用第一次变成可度量的指标。

**三、API 生命周期治理**
我把 API 治理落成一条五阶段的流水线。设计阶段**契约先行**：接口的请求响应结构、错误码、版本约定先于编码评审通过，禁止"先写实现后补文档"；评审阶段校验命名规范、幂等性、敏感数据最小化；发布阶段经 API 网关注册，配好鉴权与配额后灰度放量；版本阶段执行"只加不破"的兼容性规则——新增字段不删除旧字段、语义变更必须升主版本并设过渡期，旧版本提前 90 天通知调用方迁移；下线阶段走"标注废弃→观察期监控残余调用→正式下线归档"三步。防回归的关键一环是**契约测试**：服务提供方与各消费方在持续集成中以契约为准自动互验，接口不兼容在 CI 阶段即红灯告警，而不是等上线后被调用方投诉。项目中期一次结算服务字段调整，正是契约测试提前 3 天拦下了一个消费方的解析故障——治理的价值不在文档漂亮，而在事故消失。

**四、开放平台运营**
面向 2200 家经销商的开放平台是本轮 SOA 的"对外答卷"。技术上以 API 网关为唯一入口：每家经销商分配 AppKey 与密钥，请求以 HMAC 签名防篡改、全程 HTTPS，授权范围按最小化原则（只授其业务所需接口组）；容量安全靠配额管理：按经销商等级分配 QPS 与日调用量，超限快速失败并返回明确错误码，防止个别高频调用方挤占平台总容量。运营上我建立了三项机制：其一，接入自助化——开放门户提供在线文档、沙箱环境与密钥申请流程，经销商接入不再需要集团工程师逐家支持；其二，运营度量周报——接口调用量、错误率、慢调用 Top10 向服务责任人通报，倒逼 SLA 达标；其三，复用率考核——把"被 3 个以上消费方复用的服务占比"纳入架构组季度指标，防止资产库退化为"仓库"。上线一年，经销商在线下单占比从 47% 提升至 92%，双品类经销商"一次登录、统一订单、合并结算"的核心诉求落地。

**五、成效、不足与体会**
项目各项指标：130 项服务资产、新应用集成周期 6 周缩短至 5 天、API 复用率 68%、集成类故障下降 74%、经销商在线订单占比 92%。不足有三：其一，初期服务粒度失控——个别团队把一个页面交互包装成"服务"，后来经架构委员会两次专项整治才收敛，说明服务识别的准入标准应在项目早期就成文；其二，契约测试初期只覆盖核心服务（约 40%），一次一般服务的不兼容变更仍逃逸到生产，覆盖率必须持续爬坡；其三，复用率考核出现指标导向偏差——有团队为凑复用强行归并无业务关联的接口，考核须与业务价值评估并用。我的体会是：SOA 的成败三分在技术、七分在治理——技术组件随时可以替换，而"把能力沉淀为可复用资产、用生命周期纪律保持资产健康、用运营指标牵引资产增值"这套机制才是架构师真正要经营的产品；接口越攒越多时，资产库的秩序就是企业的秩序。
