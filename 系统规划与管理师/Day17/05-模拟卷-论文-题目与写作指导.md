## 试题一：论信息系统总体架构设计

**题目要求：**
总体架构设计是信息系统规划的成果核心，业务、数据、应用、技术四层架构自上而下牵引、自下而上支撑。

请以"论信息系统总体架构设计"为题，围绕以下三个方面论述：
1. 概要叙述你参与的架构设计项目（背景、规模、周期、你的岗位职责）；
2. 结合项目论述四层架构的设计方法、关键决策与架构治理；
3. 总结架构实施成效、遇到的问题及你的体会。

### 写作指导

**提纲**：摘要四句式（架构项目规模＋我的角色＋四层架构＋治理机制＋成效）→ 一、背景（多系统烟囱现状）→ 二、四层设计：业务架构（能力地图/流程）、数据架构（主数据/分层/服务化）、应用架构（组合处置新建改造退役）、技术架构（云底座/集成平台/安全）；每层一句方法＋一个本项目决策实例 → 三、关键决策与治理：两个 ADR 实例（如集成选 API 网关弃点对点；容器化取舍）、架构委员会与标准准入 → 四、总结（集成接口减少、数据贯通、交付提速数据＋不足＋体会：架构是共识与约束的产物）。

**高分要点**：四层每层有"产出物实例"；两个架构决策有背景-方案-理由；治理机制不缺席。
**常见失分**：四层内容互相串（数据写进应用层）；无决策过程；无治理。

### 试题一 参考范文

**【摘要】**

2023年9月，我作为系统规划与管理师担任某省政务服务大数据局"一体化政务服务平台"的总体架构师，负责信息系统的总体架构设计。该平台需整合全省42个厅局的1800余项政务服务事项，支撑"一网通办"，日均办件量高峰达300万件。本文结合该项目论述信息系统总体架构设计的过程与方法：架构规划上，采用"业务架构→应用架构→数据架构→技术架构"四层递进的总体框架——业务架构以政务服务全流程为主线识别业务能力，应用架构设计"前台受理、中台支撑、后台管理"的分层结构，数据架构确立政务数据共享交换与主题库建设，技术架构确立政务云与微服务技术基线；架构决策上，对集成方式、部署模式等关键决策采用多方案比较与决策记录；架构治理上，建立架构评审委员会与架构基线管理，42个接入厅局的技术方案必须通过架构符合性审查。平台2024年上线后，政务服务事项网上可办率达96%，"最多跑一次"事项占比89%，一次联办场景平均办事时限压缩62%，总体架构成为平台稳定演进的基石。

**【正文】**

**一、项目背景与架构挑战**

该项目是全省深化"放管服"改革的头号工程：要让企业和群众"进一张网、办所有事"。架构挑战来自三方面：业务上，42个厅局的事项流程各异、数据标准不一，"一件事一次办"需要跨部门流程重构；技术上，既有各厅局垂直系统需保留运行又必须互联互通，新旧共存周期长；规模上，全省统一平台的高并发（峰值300万件/日）与高可用（政务服务的政治敏感性）要求苛刻。我作为总体架构师的工作准则有三条：架构服务于业务战略（"一网通办"决定一切设计）、演进式设计（不求一步到位、但求步步可扩展）、以数据为中心（政务的核心资产是数据）。总体设计按业务、应用、数据、技术四层递进展开——上层定义下层、下层支撑上层，这个顺序不能颠倒。

**二、业务架构与应用架构：从政务流程到系统分层**

业务架构设计从政务服务全流程入手。我组织对1800余项事项做流程梳理，抽象出"受理、审批、制证、送达、评价"五个通用环节与"编办管理、事项管理、办件流转"等九大业务能力域；同时以"新生儿出生一件事"等20个高频联办场景为样本，识别跨部门流程的整合点——这些场景涉及5至8个厅局的数据共享与流程串联，是检验架构的业务试金石。应用架构上，我设计了"前台—中台—后台"分层结构：前台层建设统一受理门户（PC端、APP、大厅自助终端多渠道一致体验）与省市县乡村五级贯通的受理体系；中台层沉淀共享能力——用户认证中心（全省统一实名认证）、电子证照中心（一次生成、全域互认）、办件流转引擎、支付中心，中台的价值就是让42个厅局不必重复建设这些能力；后台层为各厅局审批系统与业务系统，通过标准接口接入。这个分层的关键决策是"中台厚、后台松"：中台由省里统一建设强管控，后台保留厅局系统的自主性，只约束接口标准——既快速实现统一体验，又避免了"推倒重来"的政治与成本阻力。

**三、数据架构与技术架构：数据为中心的底座**

数据架构是政务平台的命脉。我设计了"一个共享交换体系＋四类库"的结构：共享交换体系是数据流动的血管，基于目录式的共享机制，各厅局数据"以共享为原则、不共享为例外"，敏感数据经授权调用；四类库为人口、法人、电子证照等基础数据库，办件过程库，政务服务主题库（如"一件事"主题包），与分析决策库。数据标准上，我主持制定全省统一的事项编码、办件标识、证照目录三类标准——事项编码统一后，跨厅局的事项关联才成为可能。技术架构上确立三条基线：部署基线为省级政务云集中部署、边缘节点分布式受理（乡镇网点弱网可办）；应用基线为微服务架构，办件引擎、证照中心等核心能力独立部署、独立扩展，支撑300万件/日峰值——一次"社保年审"高峰验证了弹性设计的价值，自动扩容消化了3倍洪峰；集成基线为统一服务网关与接口标准，1800余项事项的跨部门调用全部经网关，为审计与治理留痕。技术选型我坚持"成熟优先、自主可控"，核心组件采用国产化软件，符合政务领域的政策要求。

**四、架构决策与治理：让架构有据可依、有人守护**

架构设计充满权衡，我坚持"决策留痕"。三个关键决策的记录成为项目资产：其一，集成方式上比较了"接口直连、总线、服务网关"三方案，最终选服务网关——兼顾性能与治理；其二，事项办理的流程引擎上比较"集中引擎与厅局自建"，选集中引擎——"一件事"联办的流程一致性高于厅局灵活性；其三，历史数据上选择"原库保留、按需迁移"——避免全量迁移的巨大风险。每个决策记录（背景、备选、结论、理由）编入架构文档，避免了"为什么当初这么设计"的反复争议。架构治理上，我推动建立平台架构评审委员会：42个接入厅局的技术方案（接口规范、数据对接、安全要求）必须通过架构符合性审查方可上线，两年间评审方案180余个、退回整改31个，其中多家厂商方案采用点对点直连绕过网关，全部整改后接入——没有这道闸门，平台两年内就会退回接口蛛网时代。

**五、成效、不足与体会**

平台2024年6月上线，政务服务事项网上可办率96%，"最多跑一次"占比89%，20个"一件事"场景平均办事时限压缩62%，架构经受住了上线后首个办事高峰的考验。不足与体会：一是四层架构的落地深度不一，数据架构的现实阻力最大——个别厅局视数据为部门权力，共享靠省政府文件与考核双管齐下才推进，这让我认识到架构问题从来不只是技术问题，数据架构的本质是权责结构；二是中台能力建设与厅局需求的节奏错配，中台未就绪时两个厅局先行自建了证照模块，后续迁移花费了额外成本——演进式架构要求"基线先行"，共享能力要抢在个性化需求之前建成；三是架构文档的维护投入常被低估，我配置了专职架构管理员保持文档与实际一致。我的总体体会是：总体架构设计是"把战略翻译成结构"的艺术——四层递进保证翻译的完整性，决策记录保证翻译的可追溯，治理机制保证翻译不被执行走样；架构师的功力不在画出多漂亮的图，而在让图上的每一个决策都经得起两年后回看。

## 试题二：论网络与信息安全体系规划

**题目要求：**
依据等级保护制度并融合纵深防御思想，构建覆盖边界、网络、主机、应用、数据的安全体系，是信息系统安全规划的主流方法。

请以"论网络与信息安全体系规划"为题，围绕以下三个方面论述：
1. 概要叙述你参与的安全体系规划项目（系统背景、定级情况、周期、你的岗位职责）；
2. 结合项目论述等级保护工作流程与纵深防御体系（边界/网络/主机/应用/数据/管理）的设计落地；
3. 总结建设成效、遇到的问题及你的体会。

### 写作指导

**提纲**：摘要（系统背景与定级三级＋我的角色＋等保流程＋纵深六层＋成效：通过测评、事件下降）→ 一、背景（系统概况与定级论证）→ 二、等保流程五动作按时间线展开（重点：差距分析与整改设计）→ 三、纵深防御落地：每层一个具体措施实例——边界（下一代防火墙＋IPS/WAF）、网络（分区与 VLAN/零信任试点）、主机（基线加固与漏扫）、应用（上线前渗透/SDL）、数据（加密/脱敏/审计）、管理（制度/岗位/演练）＋堡垒机与日志审计贯穿 → 四、总结（测评通过、告警与事件数据、不足：初期重设备轻运营、体会：三分技术七分管理、安全左移与持续运营）。

**高分要点**：等保五动作与项目时间线咬合；六层防御每层一实例不空谈；管理与技术并重。
**常见失分**：设备清单堆砌；漏管理等保流程；无演练/意识教育。

### 试题二 参考范文

**【摘要】**

2024年1月，我作为系统规划与管理师主持了某三甲医院集团的网络安全与信息安全体系规划项目，担任安全规划负责人。该集团拥有4家医院、8000余张床位，信息系统承载HIS、EMR、PACS等120余个系统，日均诊疗量3万人次，历史发生过勒索病毒事件导致挂号中断。本文结合该项目论述网络与信息安全体系规划：安全需求分析上，从业务连续性、患者隐私保护、合规监管三个维度识别安全需求，确定"等保三级为基线、诊疗业务零中断为底线"；体系设计上，按"技术、管理、运营"三位一体构建——技术上实施网络分区分域（内外网物理隔离、诊疗区与办公区VLAN分离）、纵深防御（边界防护、入侵检测、终端管控、数据加密、审计溯源五层）、敏感数据分级保护；管理上建立三级安全组织与制度体系；运营上建设安全监控中心（SOC），实施漏洞全生命周期管理与常态化攻防演练；实施路径上按"紧急加固、体系建设、持续运营"三期推进。体系建成一年后，集团通过等保三级测评，安全事件同比下降81%，两次成功防御勒索病毒攻击，诊疗业务实现安全事件零中断。

**【正文】**

**一、项目背景：医疗行业的安全之痛**

医疗行业的信息安全有独特痛点：业务"停不起"——挂号收费停一小时，全院数千患者积压；数据"丢不起"——病历与检查影像是诊疗依据，丢失即是医疗事故；隐私"泄不起"——患者诊疗信息是高价值隐私数据，泄露面临监管处罚与声誉危机。而该集团的现状令人担忧：内外网边界模糊，医生站可随意插U盘（两年前的勒索事件正源于此）；120余个系统分属不同厂商，账号权限混乱，离职人员账号未清理；安全设备仅有老旧防火墙，日志留存不足。我主持规划时的总体思路是：不做设备堆砌式的"买安全"，而是建体系化的"治安全"——安全体系必须同时回答"防得住、管得住、看得见"三个问题，对应技术、管理、运营三大支柱。

**二、安全需求分析与总体框架设计**

规划从需求分析起步。业务连续性需求：按诊疗业务分级，挂号收费与HIS为最高级，要求任何安全事件不得中断核心诊疗；患者隐私需求：梳理出患者身份、诊疗记录、检验报告、影像四类敏感数据，按数据安全法规要求分级管控；合规需求：医院信息系统按监管要求需通过等保三级测评。总体框架设计上，我确立了"一个中心、三重防护、三期演进"的架构：以安全运营中心（SOC）为核心，构建通信网络、区域边界、计算环境三重防护（对齐等保设计方法），按紧急加固、体系建设、持续运营三期落地，总投资规划1200万元分两年投入。框架设计中最关键的取舍是"内外网隔离"：我力主医疗设备网、诊疗业务网与互联网访问彻底分离——医生办公上网走独立互联网出口，与诊疗网物理隔离，这一决策在后来两次勒索攻击中被证明是"保命设计"。

**三、技术防护体系：分层纵深、数据为核**

技术体系按纵深防御原则五层布防。边界防护层：互联网出口更新为下一代防火墙并串联入侵防御，远程访问全部经VPN双因素认证；网络分区分域层：全集团划分诊疗核心区、办公区、互联网区、DMZ区、无线接入区，VLAN间访问策略化管控，PACS影像传输的巨大流量单独规划通道避免挤占业务；终端与主机层：全院1.2万台终端统一部署企业级杀软与准入控制（不合规终端禁入网络），服务器实施基线加固与补丁管理，封禁非必要外设；数据保护层：这是医疗行业的重心——患者敏感数据实施分级管理，数据库启用透明加密，测试环境全部脱敏，病历数据导出须审批留痕，核心数据"本地备份＋异地容灾"双保障，RPO不超过15分钟；审计溯源层：部署数据库审计与堡垒机，运维操作与敏感查询全量留痕，为安全事件追溯与内部威慑提供依据。数据安全的技术措施我坚持"场景化"：如科研要用真实病例，我们提供脱敏后的科研数据集，而不是简单禁止——堵疏结合才可持续。

**四、管理体系与安全运营：三分技术、七分管理**

管理体系建设分三块。组织制度上，集团成立网络安全委员会（院长任主任），信息科设安全专岗，各院区设安全员，三级责任落实到人；制度体系编制"总体策略＋18项管理制度＋操作规程"三层文件，覆盖账号、变更、介质、外包、应急等场景，全部经委员会发布并纳入考核。人员教育上，全员年度安全培训与钓鱼演练常态化——首次钓鱼演练点击率19%，三次后降至4%；对信息科运维团队开展攻防技能实训。安全运营是我最看重的板块：建成SOC安全监控中心，日志集中采集留存180天，安全事件分级响应（重大事件15分钟集结、1小时处置）；漏洞管理全生命周期化——月度扫描、高危漏洞48小时修复闭环，全年修复高危漏洞230余个；每半年一次红蓝攻防演练，检验体系实战性。运营数据月度形成安全报告，向委员会汇报——安全态势"看得见"，才谈得上"管得住"。

**五、成效、不足与体会**

体系建成一年：集团四院区核心系统全部通过等保三级测评；安全事件同比下降81%，两次勒索病毒攻击在边界即被拦截、诊疗业务零中断；钓鱼演练点击率降至4%，全员安全意识明显改善。不足有三：一是医疗设备网的老旧操作系统无法打补丁，只能靠网络隔离兜底，这类"带病运行"是行业性顽疾；二是安全人才短缺，SOC初期只能做到事件看得见、分析依赖厂商，我们通过"厂商驻场＋自有人员跟学"逐步实现自主运营；三是安全投入的显性收益难量化，第二年预算论证时我用"两次勒索拦截避免的潜在损失估算（参照同业事故）"才说服了财务——安全的价值在于"没有发生的事故"，这需要用数据讲故事。我的体会是：第一，医疗安全规划的第一原则是"业务连续性优先"，任何安全措施不能以中断诊疗为代价；第二，纵深防御的实质是"假设任一层会被突破"，层层设防提高攻击成本；第三，安全是运营出来的不是建设出来的——SOC、演练、漏洞闭环这些日常动作才是体系的生命力；第四，把"人"纳入防护体系（培训、演练、意识），因为最坚固的防火墙也会被一次点击绕过。
